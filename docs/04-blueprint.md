# 04 — The Blueprint

The blueprint is the contract between "what we found in AWS" and "what we run
locally." It is the only artifact the user is expected to read, edit, review in a
PR, and commit.

## Two files, one merge

| File | Owner | Committed | Regenerated |
| --- | --- | --- | --- |
| `cloud-echo.yaml` | generated by `plan` | yes | **fully overwritten** on re-plan |
| `cloud-echo.override.yaml` | the human | yes | never touched |

Effective config = `cloud-echo.yaml` deep-merged with `cloud-echo.override.yaml`,
override wins. Docker Compose's model, and familiar for the same reason: it makes
regeneration safe. There is no three-way merge, no conflict markers, no "cloud-echo
ate my edits."

`cloud-echo plan --diff` shows what a re-plan would change before writing.

## Design constraints

1. **Deterministic serialization.** Stable key order, stable list order, stable
   formatting. A blueprint diff must reflect real infrastructure change, not map
   iteration order. Non-negotiable: this file lives in git.
2. **No secret values, ever.** Only references and placeholders.
3. **Self-contained enough to run without AWS.** Given the blueprint plus Docker,
   `up` must work with no credentials. This is what makes CI usage possible later.
4. **Provenance embedded.** Which account, which region, which scan, which
   cloud-echo version, what seed and depth produced it.
5. **Human-writable.** A user must be able to hand-author a blueprint from scratch
   without ever running a scan. If the format is only machine-friendly, we've
   built a lock-in, not a tool.

## Reference syntax

Values that must resolve at materialization time use `${...}`:

```yaml
env:
  QUEUE_URL:  ${ref:sqs/orders-events.url}
  TABLE_NAME: ${ref:ddb/orders.name}
  DB_HOST:    ${ref:rds/orders-db.host}
  PAYMENTS:   ${ref:ext/payments-api.url}
  REGION:     ${meta:region}
```

Anything not wrapped in `${...}` is a literal and is passed through untouched.

Two attributes must *always* be references, never literals copied from the scan,
because their values differ per environment by construction (measured in
[m1-real-account-findings.md](spikes/m1-real-account-findings.md)):

- `${ref:sqs/x.url}` — the URL embeds the endpoint (`https://sqs.<region>…` in
  AWS, `http://floci:4566/…` locally).
- `${ref:ddb/x.streamArn}` — the stream label is its creation timestamp.

API Gateway APIs are identified by API id in the inventory, because names are not
unique; the `apigw/public` in the example below is shorthand the planner derives
from the name, disambiguating when two APIs share one.

Event sources on a function are keyed by `from:` (and the function's qualifier),
never by the mapping's UUID, which is minted per environment.

**What database refs resolve to.** M0 found that Floci *proxies* RDS and
ElastiCache connections: `DescribeDBInstances` reports the **Floci container's**
address, not the backing Postgres container's. So `${ref:rds/x.host}` resolves to
the **Floci container name** (stable across restarts), never the reported IP
(which changes) and never the backing container.

For ElastiCache, Floci returns `NodeGroups: null`, so there is no discoverable
endpoint at all — cloud-echo synthesises one from the Floci host plus the
conventional port. Known gap, tracked in
[spikes/m0-findings.md](spikes/m0-findings.md#d4--ref-targets-for-rds-and-elasticache).

## Schema (v1 draft)

```yaml
version: 1

metadata:
  generatedBy: cloud-echo/0.1.0
  generatedAt: 2026-08-27T14:02:11Z
  source:
    accountId: "123456789012"     # used as local account id; ${meta:account}
    accountAlias: prod
    region: us-east-1
    scanId: 01J8ZQ...
  seed: [ecs/orders-api]
  depth: 2

runtime:
  floci:
    image: floci/floci:1.4
    port: 4566
    storage: hybrid               # memory | persistent | hybrid | wal
  network: cloud-echo
  gateway:
    port: 7070
    defaultMode: mock             # mock | passthrough | record | replay
  platform: linux/amd64           # override per-container as needed

# ---------------------------------------------------------------- data plane
resources:
  - id: ddb/orders
    type: dynamodb.table
    origin: { arn: "arn:aws:dynamodb:us-east-1:123456789012:table/orders" }
    spec:
      tableName: orders
      keySchema:
        - { name: pk, type: S, role: HASH }
        - { name: sk, type: S, role: RANGE }
      globalSecondaryIndexes:
        - { name: gsi1, keySchema: [{ name: gsi1pk, type: S, role: HASH }] }
      stream: { enabled: true, viewType: NEW_AND_OLD_IMAGES }
    data:
      mode: none                  # none | fixtures | generated
      fixtures: ./fixtures/orders.jsonl

  - id: sqs/orders-events
    type: sqs.queue
    spec:
      queueName: orders-events
      visibilityTimeout: 30
      dlq: { target: sqs/orders-events-dlq, maxReceiveCount: 5 }

  - id: rds/orders-db
    type: rds.instance
    spec:
      engine: postgres
      version: "16.3"
      port: 5432
      database: orders
      # credentials are LOCAL ONLY and intentionally weak
      username: postgres
      password: postgres
    data:
      mode: migrations
      migrations: ./migrations    # run after the container is healthy

  - id: cache/sessions
    type: elasticache.cluster
    spec: { engine: valkey, version: "8", port: 6379 }

  - id: secret/orders-db
    type: secretsmanager.secret
    spec:
      name: prod/orders/db
      # value NEVER comes from AWS; this is a local placeholder
      value: ${ref:rds/orders-db.connectionJSON}

# ---------------------------------------------------------------- workloads
workloads:
  - id: ecs/orders-api
    type: ecs.service
    origin: { arn: "arn:aws:ecs:...:service/main/orders-api" }
    runtime: floci-ecs            # floci-ecs | docker  (see 05)
    spec:
      cluster: main
      desiredCount: 1             # downscaled from 4
      taskRole: orders-api-task   # materialized as local IAM role
      containers:
        - name: app
          image:
            mode: ecr             # ecr | build | image
            repository: 123456789012.dkr.ecr.us-east-1.amazonaws.com/orders-api
            tag: v1.42
            digest: sha256:9f2b...        # pinned at plan time
          ports: [{ container: 8080, host: 8080 }]
          env:
            TABLE_NAME:   ${ref:ddb/orders.name}
            QUEUE_URL:    ${ref:sqs/orders-events.url}
            DB_HOST:      ${ref:rds/orders-db.host}
            PAYMENTS_URL: ${ref:ext/payments-api.url}
            LOG_LEVEL:    info
          secrets:
            DB_PASSWORD: { from: secret/orders-db, key: password }
          healthcheck:
            path: /health
            interval: 10s

  - id: lambda/order-processor
    type: lambda.function
    spec:
      functionName: order-processor
      runtime: nodejs20.x
      handler: index.handler
      memory: 512
      timeout: 30
      code:
        mode: local               # local | s3 | ecr | stub
        path: ../order-processor/dist
      env:
        TABLE_NAME: ${ref:ddb/orders.name}
      eventSources:
        - { from: sqs/orders-events, batchSize: 10 }

# ---------------------------------------------------------------- edge
edge:
  - id: apigw/public
    type: apigateway.v2
    spec:
      port: 8080
      routes:
        - { method: POST, path: /orders,      target: ecs/orders-api }
        - { method: GET,  path: /orders/{id}, target: ecs/orders-api }
        - { method: POST, path: /webhooks/pay, target: lambda/order-processor }

# ---------------------------------------------------------------- integrations
integrations:
  - id: ext/payments-api
    type: http
    discoveredFrom: "ecs/orders-api env PAYMENTS_URL"
    upstream: https://api.payments.example.com
    mode: mock
    rules:
      - name: charge-ok
        match: { method: POST, path: /v1/charges }
        respond:
          status: 201
          headers: { content-type: application/json }
          body: { id: ch_local_1, status: succeeded }
      - name: default
        match: { path: "**" }
        respond: { status: 501, body: { error: "no mock defined" } }

  - id: ext/legacy-inventory
    type: http
    upstream: http://inventory.internal.corp
    mode: mock
    rules:
      - match: { path: "**" }
        respond: { status: 200, body: { available: true } }

# ---------------------------------------------------------------- graph
graph:
  nodes:
    - { id: ecs/orders-api, flow: sync }
    - { id: lambda/order-processor, flow: async }
  edges:
    - from: apigw/public
      to: ecs/orders-api
      kind: http
      confidence: certain
      evidence:
        - rule: apigw.integration
          source: "apigatewayv2:GetIntegration api-8f2b/int-9c1"
          detail: "VPC_LINK → alb/orders-public → tg/orders-api"
    - from: ecs/orders-api
      to: ddb/orders
      kind: write
      confidence: high
      evidence:
        - rule: iam.policy-resource
          source: "iam:GetRolePolicy role/orders-api-task"
          detail: "Allow dynamodb:PutItem,UpdateItem on table/orders"
        - rule: config.value-scan
          source: "ecs:DescribeTaskDefinition orders-api:41 env TABLE_NAME"
          detail: "value 'orders' matches ddb/orders"
```

## Override file

```yaml
version: 1

workloads:
  - id: ecs/orders-api
    runtime: docker               # hot-reload loop instead of Floci ECS
    spec:
      containers:
        - name: app
          image:
            mode: build           # build from a local checkout instead of ECR
            context: ../orders-api
            dockerfile: Dockerfile.dev
          mounts:
            - { host: ../orders-api/src, container: /app/src }
          env:
            LOG_LEVEL: debug

integrations:
  - id: ext/payments-api
    mode: record                  # hit the real thing once, then replay
    cassette: ./cassettes/payments

graph:
  edges:
    remove:
      - { from: ecs/orders-api, to: ddb/audit-log }   # wrong inference
    add:
      - { from: ecs/orders-api, to: sqs/notifications, kind: publish }
```

List merging is by `id`, not by index — merging by position on a regenerated file
would silently reassign overrides to the wrong resource. `graph.edges` is the one
place using explicit `add`/`remove` because edges have no natural single key.

## Validation

`cloud-echo validate` runs on every `plan` and `up`:

- schema conformance
- every `${ref:...}` resolves to a declared resource and attribute
- no dangling edges
- no port collisions on the host
- no secret-looking literals (entropy + key-name heuristics) → hard error, with
  guidance to use `secrets:` instead. This is the guardrail that keeps credentials
  out of a committed file.
- image platform vs host arch → warning, not error
