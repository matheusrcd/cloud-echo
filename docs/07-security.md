# 07 — Security & Trust Model

cloud-echo asks for credentials to a production AWS account. That is a large ask,
and adoption depends entirely on the answer being obviously safe. Every guarantee
below must be *structural* — enforced by code that cannot be bypassed by mistake —
not a promise in a README.

## Guarantee 1 — Structurally incapable of writing to AWS

The AWS client used for discovery carries a middleware that rejects any operation
not on an **explicit allow-list** of exact `service:Operation` pairs
([`internal/awsx/operations.go`](../internal/awsx/operations.go)). The
`Describe`/`List`/`Get`/`BatchGet` naming check runs too, but only as defence in
depth — it is not the control.

> **This started as a prefix-only check and the prefix was not enough.**
> `GetSecretValue`, `GetFederationToken`, `GetSessionToken`, and
> `GetPasswordData` all begin with `Get`. A prefix-only guard would have permitted
> every one of them, including the call Guarantee 2 below exists to forbid — so
> the guard would have contradicted the security model it was written to enforce.
> `TestGuardBlocksReadLookingNamesNotOnTheAllowList` pins each of them by name.

```go
switch {
case op == "":                   // metadata missing → fail closed
case !hasReadPrefix(op):         // defence in depth
case !IsAllowed(service, op):    // the actual control
}
```

Properties that make this worth doing:

- The allow-list is **one flat list**, auditable in a minute by a skeptical
  security reviewer, and it is the single source of truth for the middleware, the
  shipped IAM policy, and `scan --dry-run`. They cannot disagree.
- The guard registers at `Initialize/Before`, ahead of the SDK's own input
  validation. That is about the error the user sees, not about safety: run it
  later and a malformed mutating call reports "missing required field" for a
  request cloud-echo was never going to send.
- Every degradation path ends in *refuse*. If a future SDK stops populating the
  operation name, the empty string is not on the allow-list, so everything blocks
  and the breakage is loud.
- Tests assert the block happens **before anything reaches the network**, not just
  that an error comes back.
- There is **no flag to disable it.** Not `--force`, not an env var. The moment an
  escape hatch exists, the guarantee is gone.

The materializer uses a *separate* client whose endpoint is hardcoded to the local
Floci instance, and which refuses to resolve any endpoint outside `localhost` /
the project docker network. Read path and write path cannot be confused, because
they are different types.

## Guarantee 2 — Secret values never leave AWS

- `secretsmanager:GetSecretValue` is **not** in the scanner policy and not in the
  read-only allow-list for the Secrets Manager collector.
- `ssm:GetParameter` is used only with `WithDecryption=false`, and `SecureString`
  parameters are recorded as name + type only.
- RDS master passwords are never read; local databases get local-only credentials
  generated by cloud-echo.
- The blueprint is scanned before write for high-entropy strings and
  secret-shaped key names (`*_SECRET`, `*_TOKEN`, `*_PASSWORD`, `*_KEY`,
  `AKIA*`, PEM headers). A hit is a **hard error**, not a warning.

`--include-secret-values` does not exist. If you want a real secret locally, you
put it in `cloud-echo.override.yaml` — which the repo's `.gitignore` template
covers — or reference it from your own environment.

## Guarantee 3 — No data exfiltration, no telemetry

- No analytics, no crash reporting, no version-check phone-home, no anonymous
  usage stats. Not opt-out — absent.
- The only outbound connections cloud-echo makes are: the scanned AWS account's
  API endpoints, container registries for image pulls, and any integration the
  user explicitly put in `record`/`passthrough` mode.
- `cloud-echo scan --dry-run` prints every API call it would make and exits
  without loading credentials, so a security team can review the surface before
  granting access. Its output is generated from the same allow-list the
  middleware enforces, so it cannot understate what the tool does.

## Production data

The default is **no production data locally**. Copying real customer records onto
a laptop is a compliance incident, and a tool that makes it a one-liner will be
banned by every organisation that matters.

`data.mode` per resource:

| Mode | Behaviour |
| --- | --- |
| `none` | Schema only. **Default.** Empty tables and databases. |
| `fixtures` | Load from user-authored files committed to the repo. |
| `generated` | Synthesise plausible rows from the key schema and attribute types. |

`import` (pull real rows from the real account) is deliberately **not implemented
in v1**. It is the single most requested feature that would most damage the
project's credibility if shipped carelessly. If it is ever added it must be:
opt-in per resource, capped, redaction-mandatory, and require a distinct IAM
permission the scanner policy does not grant — so an organisation can allow
scanning while forbidding data extraction.

## What the blueprint still reveals

Even with zero secrets, `cloud-echo.yaml` contains internal topology: service
names, queue names, table schemas, VPC layout, third-party vendor hostnames. For
most teams that is fine in a private repo. For a public one it is not.

- `cloud-echo plan --sanitize` replaces the account ID, aliases resource names
  through a stable hash, and strips ARNs — producing a shareable blueprint that
  still runs.
- `docs`, `README`, and `plan` output all state clearly that the blueprint is
  internal-topology-sensitive by default.

## Local environment hardening

The local stack is deliberately insecure — trivial database passwords, no TLS
between containers, permissive local IAM. That is correct for a dev environment
and dangerous if exposed:

- All host ports bind to `127.0.0.1` by default, never `0.0.0.0`.
  `--bind 0.0.0.0` exists for devcontainer/remote setups and prints a warning.
- The gateway's generated CA is per-project, stored in `.cloud-echo/ca/` with
  `0600`, gitignored, and never installed into the host system trust store —
  only into containers. A tool that silently adds a CA to your machine's trust
  store is malware-shaped, regardless of intent.
- `down --volumes` genuinely removes volumes, including any recorded cassettes
  that may contain real responses.

## Supply chain

- Reproducible builds, checksums published per release.
- Dependencies kept minimal and pinned; `go.sum` verified in CI.
- Release binaries signed; container images published with provenance
  attestations.
- No `curl | sh` as the recommended install path.
